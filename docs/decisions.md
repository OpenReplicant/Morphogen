# Decisions (rebuild 5)

Append-only. Rebuild 4's decisions (OpenReplicant/kernel, `docs/decisions.md`, D-01 to D-93) stay
settled unless an entry here supersedes one. Status: **decided** (owner agreed), **adopted** (taken on
recommendation; confirm or overturn), **proposed** (needs the owner). **delegated**: the owner left the
decision to the agent (Oct 2026: "I'm going to let you make these decisions"); it stands as decided.

| R5-10 | **The feed, as-of reads and the no-extension check (T1; the kernel change D-86/D-87(a) allowed).** (a) The feed is its own table, `kernel.feed(seq, change_set, scope)`, written by apply, readable by scope (RLS), so feed readers need no access to `kernel.change_set`, whose ops stay visible only to submitters, validators and reviewers. (b) Numbers come from a one-row counter that apply locks until commit, not from a sequence: with a sequence, a change set that commits later can hold a smaller number, and a cursor already past it skips it for good (the mutant that uses a sequence fails the concurrent-commit case). The cost is that applies serialize from the end of apply to commit. A concurrency failure there (serialization, deadlock, lock timeout) is raised for the caller to retry, never recorded as an invalid change set. Accepted: gaps in a reader's numbers show how many change sets were applied in scopes it cannot read, and when. (c) `api.claims_as_of(valid_at, known_at)` returns claims recorded by `known_at` and true at `valid_at`, with the status and belief recorded by then; redaction holds at every time. Limits, accepted for now: record times are transaction start times, so an answer for a past `known_at` can still change until transactions open at that time have committed (R5-O4); belief is read for the currently active belief model. (d) "No extension code in the commit" is checked on the catalog, over every function reachable from a kernel table: triggers run kernel-owned functions in SQL or PL/pgSQL; defaults, constraints, policies and rules call only kernel or catalog functions; kernel function bodies name no other schema's functions; definer functions pin their search path; no extension owns kernel objects; only the kernel owner can create in the kernel schema. (e) The feed test opens concurrent sessions through `dblink`, installed in the test database only | delegated |

| R5-13 | **T3 ports, and how services wake.** (a) `kk.lib` and `kk.changes` come from rebuild 4 into `kernel/src/kk/`; services keep their code shape. (b) Hooks before the commit (the validator) act on submitted change sets, which the feed never carries, so they keep NOTIFY plus a sweep (`listen`). Consumers after the commit (belief, verifier, recall index) `follow` the change feed: they poll `api.feed` after an in-memory cursor (the starting head is read from `kernel.feed`, granted to agents under the same row-level security) and still re-read the record from their own watermark, so nothing is missed while one is down; a durable per-consumer cursor is not needed yet (R5-O5). The recall index also listens on `kernel_redaction` (redactions are not in the feed, R5-O3). Wake rules: belief and the recall index wake on any applied change set, their own included (that step submits nothing and ends the round); the verifier only on change sets that touched claims (rebuild 4: any applied). (c) Ported as Morphogen needs them (R5-12): kernel-mcp's operator tools, not its memory profile or briefing; BM25 recall, not dense fusion or re-ranking. (d) Rebuild 4 gaps fixed on the way, in kernel-mcp: `whoami` failed for every agent that is not a reviewer (it read `api.review_queue` in the same statement; now only when the caller may read it); stdio refused only superusers and `kk_authenticator` by name, and now refuses any login that can create roles, bypass row-level security or act as another agent's role. (e) The SciFact retrieval eval moves to `kernel/evals/scifact` with the abstracts encoded as rebuild 4's paper encoder did (that module stays parked); it is run by hand, not in CI (3 minutes, CC BY-NC data): nDCG@10 0.6606, recall@200 claims 0.9382 against rebuild 4's 0.6594 and 0.9349: a match, not an improvement (here no paper claim has a belief to break ties, and the background corpus is smaller) | delegated |
| R5-14 | **The self-encoder records structure from files, and the pack loader comes first (T4).** (a) The pack loader is ported (rebuild 4, `packs.sql` identical but for paths): the self-encoder's terms (kk-core, dcterms) must be approved before any of its claims apply. (b) The self-encoder reads `kernel/blueprint/slots.yaml`, every `kernel/providers/*/provider.yaml` and distribution files it is given (the kernel never names a distribution's path). Every claim cites its file and line (RFC 5147 fragment); a line that cannot be found is an error, never another line's citation. Each change set's key names the file's content and the change set it follows, so the same content again is a no-op while a reverted or restored file is recorded again; a kernel file gone from disk is retracted, a distribution only with `--forget`. The claims go to `urn:kk:scope:vocab` (slot and provider descriptions, as the bootstrap labels it). (c) Providers are not typed `kk:Module` yet: that type needs a module kind and an agent the manifests do not carry, and typing one goes to review; the manifests gain those fields when `module.schema.json` is adapted. (d) `self_encoder answer` is the check: which provider fills each slot, from the self-encoder's own claims only (another agent's `kk:fills` does not count), with claim ids, belief and file:line; a slot not in the record says so | delegated |

| R5-16 | **Redactions are in the change feed (answers R5-O3).** `kernel.feed` numbers redactions with change sets, from the same locked counter; a redaction row names its target (`target_kind`, `target_id`) and takes the target's scope, so readers without clearance do not see it. `api.feed` gains `kind` ('change_set' or 'redaction'), `target_kind` and `target_id`; for a redaction, `claim_ids` are the claims whose content it removed (the claim, or those quoting the artifact). Redacting a target that does not exist takes no number and is not reported as an error (that would let a steward probe for targets in scopes they cannot read). A redacted artifact cannot be quoted again (KK038): a new quote would bring its content back. An artifact's row is in the artifact's scope; apply guarantees that every quoting claim's readers could read the artifact (KK035), so a reader cleared later for a claim's scope but not the artifact's misses the row (accepted). A redaction holds the feed counter until commit, so stewards redact in short transactions. `pg_notify('kernel_redaction')` stays as an immediate signal only. recall-bm25 follows the feed and drops every redacted claim it still holds by claim id, not by time; the quote verifier wakes on change sets only. Contract 0.3.0: seven feed cases and one redaction case, six mutants | delegated |

| R5-20 | **T5: the bootstrap loop on Morphogen's own stack.** (a) *Monitor.* Providers report metrics as OpenTelemetry: `kk.telemetry` (standard library, OTLP/HTTP JSON, on only when the standard `OTEL_EXPORTER_OTLP_*` variables are set) and `kk.lib.follow` reports `kk.feed.lag` (commit to read) and `kk.step.duration`. Telemetry is a wire format, not a slot: any OTLP receiver can take it. `observer-otel` is that receiver (JSON or protobuf) and records each window's mean per resource and mapped metric as a SOSA observation, in rebuild 4's observer shape; the observables pack gains the two properties (0.4.0). (b) *Analyse.* `anomaly` is rebuild 4's, `detect.py` unchanged, following the feed and reading any feature of interest. (c) *Plan.* The default planner is deterministic over a fixed action list (`intent/policies/actions.yaml`: today one action, the poll interval of a feed consumer, bounded and low risk); a model-driven planner is a candidate provider of the same slot, to be scored by the evaluator. A plan is p-plan, its step a `sosa:Actuation`, its risk class a `dcterms:type`, and its prediction a `bbo:maxValue` qualified by the plan (`dcterms:isPartOf`), so documented limits and predictions use one term and the anomaly module never mistakes one for the other. No new predicates. One open plan per target. (d) *Lane.* `lane-autonomy` adds `sosa:Actuation` and `p-plan:Plan` to the store's review types, so every plan waits for a person whatever lane it asks for; the autonomy matrix picks the lane a planner asks for and can only add review. Every module starts at L1; promotion above it, which must also take plan steps off the forced list for that module, is deferred (G2 onward). (e) *Execute.* `intent-actuator` keeps rebuild 4's approval rule (review lane, decided by someone other than the submitter, `api.review_decisions` ported) and commits the setting to the provider's intent file, message `change-set:<id> plan-step:<iri>`; it writes no claims, only runs. `morphogen/deploy/reconcile.py` is the bootstrap orchestrator: it runs each provider of an environment as its intent file says and restarts it when the file changes. (f) *Verify.* `prediction-verifier` (never the agent that predicted, invariant 5) takes the first 3 windows that start a settle window after the actuator's run ended and records `urn:kk:verdict:holds`, `fails`, or `untested` (the step failed or was refused) on the plan, inferred from the prediction and those observations. (g) No consumer needed a durable cursor (R5-18): anomalies, plans and verdicts are keyed by what they answer, and every pass re-reads the record. (h) The loop found two kernel slowdowns that grew with the record: `api.feed` looked up predicates with `id = any(ids)`, which scans every claim under row-level security, and the `exists (claim)` policies on references, derivations, statuses, beliefs and verifications let the planner hash every visible claim. Now a join on `unnest`, and `kernel.claim_visible(id)` (not inlinable, one primary-key lookup per row); plus indexes on `claim(predicate)` and `claim_reference(artifact)`. (i) Review fixes. Only what a person decided counts as approval: `api.review_decisions` moves into record-postgres and lists a decision only when its role is a `kernel.agent` of kind person (contract 0.4.0, with a case that no uncleared role reads rows about a secret claim; two mutants). The verifier trusts only configured observers and actuators, and never the predicting agent, for observations and runs. The OTLP receiver listens on localhost by default and takes an optional bearer token (`kk.telemetry` sends `OTEL_EXPORTER_OTLP_HEADERS`), an allow-list of services, a size cap and a clock window. The reconciler runs only intent committed at HEAD, only `python3 -m <module>` in a provider's directory, with `KK_*` settings other than `KK_ROLE`. A failed intent commit restores the file from HEAD. The planner never re-proposes for an anomaly and plans only in its own scope. Deferred, with their risk noted: each module gets its own login (today they share one that may switch to any module role) before G2; lane routing moves from the planner into the store's lane hook before any level above L1 | delegated |
| R5-21 | **T6 (G2) is test-first, and its change is a provider replacement.** (a) *Every slot declares its contract.* Each slot in `kernel/blueprint/slots.yaml` and `morphogen/distribution.yaml` has `contract:`, either a case set (`kernel/contract/slots/<slot>`, `morphogen/contract/slots/<slot>`) every provider must pass, or `provider-tests` (only the provider's own tests: a declared gap, listed by the runner) for slots without one yet. `kernel/contract/run.py` takes the providers, case sets and blueprint to check, so Morphogen runs it on its own modules; a slot with no `contract:` fails. (b) *The G2 change.* The analyser's anomaly detector gets a case set (from rebuild 4's checks, as data); a candidate analyser must pass it before anything else. The change Morphogen makes to itself is a performance one with correctness held by the case set: the incumbent rereads every observation each pass, so its step time grows with the record, which the observer sees as an anomaly on the analyser. (c) *The path.* The planner turns that anomaly into a build request (auto lane: it changes nothing running). A builder (a new Morphogen slot; CI uses a fixture builder, the gate run a model-driven one through an agent harness with `:free` models or Haiku) writes a candidate into `intent/experiments/<id>/`. A sandbox runner installs it on a sandbox database, runs the slot's case set and a benchmark on candidate and incumbent, and the evaluator records both as DQV measurements. Only a candidate that passes every case and scores above the incumbent is proposed, as a replace-provider plan with a prediction (its step time within the limit) in the review lane. A person approves; the intent actuator commits the switch; the reconciler runs the candidate; the prediction verifier checks the prediction. (d) Steps: T6a contracts, T6b sandbox and evaluator comparison, T6c builder, T6d replace-provider through plan, actuator and reconciler, T6e the end-to-end G2 test and one recorded gate run. (e) As built: a replacement keeps the slot's agent and role (the analyser stays `urn:kk:agent:anomaly`), so no database role is created at actuation; its runs name its own module, and it reports metrics under its own name, which is where the prediction is checked. A candidate runs from its experiment directory (`intent/experiments/<id>/<name>`); moving it into `modules/` is a later commit by a person. The sandbox copies the slot's benchmark inputs from the record under its own clearance and measures each provider through its own telemetry, so the sandbox and production measure the same thing; it needs a superuser login on the sandbox cluster to create databases. The planner opens one build request per provider; a request whose candidate does not do better stays open, and the person sees its measurements. The evaluator links a run to the provider it measured (`dcterms:subject`) | delegated |
| R5-22 | **Model-built code runs with the incumbent's rights and no more (T6 review).** The review found that a candidate (written by a model through the harness) ran with the trust T5 gave reviewed modules. (a) *Contract.* A case set may own its runner (set.yaml `runner:`), run on the provider's directory; then the provider's runner is not used, so a candidate cannot certify itself. The analyser's runner imports only `<package>.detect.anomalies`. A slot declared by two blueprints is refused, so a distribution cannot redeclare a kernel slot's contract. (b) *Builder.* The harness runs on a copy outside the repository and intent, with this process's environment minus `DATABASE_URL`, `PG*`, `OTEL_*`, `KK_*` and `GIT_*`; the build fails if the repository's or intent's git state changed while it ran, if the candidate holds a symbolic link, or if it carries a migration other than the incumbent's, unchanged. (c) *Logins.* A module may declare `role` and `login` (provider.yaml): a login, created by its migration, that may switch only to its role; its password is `KK_LOGIN_PASSWORD` when the cluster asks for one (`morphogen.logins`). The sandbox and the reconciler run a candidate only as the incumbent's login, with an allow-listed environment (no superuser settings, no other login); the reconciler gives a declared login to the reviewed provider too. The analyser is the first module with one. This meets R5-20's "own login before G2" for code a model wrote; the reviewed modules keep the shared login until each declares one, before any autonomy level above L1. (d) *Sandbox.* Both providers run from private copies, and the run files are written only after no provider code runs; extracted claims are not copied (a copy would need the quote; no benchmark reads them); a sandbox database is dropped on any failure. That run predates (a)-(e) | delegated |
| R5-23 | **T7: what decides a replacement is measured from outside the candidate (closes R5-22 (f)).** (a) *Benchmark.* The sandbox times full passes from its own process: `driver.py` (sandbox code, in the provider's process) imports the slot's entry, `<package>.__main__.one_pass(conn)`, connects as the incumbent's login and runs one pass per signal; the sandbox's clock times each. Before each pass the sandbox adds one new window of input (the newest copied series, one step on), as production does, so a pass that skips its work because nothing changed, or a cache, does not count. The metric is the mean of 5 timed passes after 1 warm-up (`benchmark.yaml`: `entry`, `metric: pass-seconds`, `warmup`, `passes`). The provider's telemetry no longer decides anything in the sandbox. Code in the driver's process could still cheat the clock (a pass that returns before its work is done); a person reviewing the candidate sees that. (b) *Service cases.* A slot may have service cases (`service.py` beside its case set, slot code that never imports the provider): the sandbox loads every case into one fresh database (each case's targets suffixed `-c<n>`), runs one pass of the provider as the incumbent's login, and judges the change sets it submitted against the cases' expected anomalies. The analyser has them: the same cases, now also through the service's own reading of the record. The contract a candidate must pass is both, counted together (24 for the analyser's 12 cases). A candidate that reads only providers' observations passes every rule case and fails 3 service cases. (c) *Telemetry.* With `KK_OTLP_SECRET` set, the observer accepts a request only when its bearer token is `HMAC-SHA256(secret, service.name)` for every resource in it; the reconciler gives each service its own token for its own name and never passes the secret on. A provider reports only as itself. The prediction check in production still rests on the provider's own telemetry (the code is the measured, approved code by hash, R5-22 (e)); measuring production from outside the process waits until a slot needs it. (d) The builder's prompt says how the candidate is judged (rule cases, service cases, full passes timed from outside). (e) *Gate run* (`morphogen/evals/g2/runs/2026-10-24-haiku`): Haiku's candidate reads only the newest windows per target (a real full-pass gain, 0.087 s against 0.131 s), passed the 11 rule and 11 service cases, and the verdict held. It has a bug none of the 11 cases covered: it takes the newest windows per target, not per target and property, so a target with two properties gets half the history for each. Case 12 (two properties, each with its own full history) was added; the incumbent and the fixture pass it, the candidate fails it. The case set is what stands between a model's change and a person's approval, so a bug found in a candidate becomes a case | delegated |
